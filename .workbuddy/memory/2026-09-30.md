### 沉淀

- **`wx.showModal({editable:true})` 的返回值是 promise，`success()` 只是 resolve。**
  测试里手工触发 `success()` 之后必须等一拍再断言，否则同步断言会「假绿」——
  这次差点又栽在「降级/异步路径没被真正覆盖」上（第 10 轮踩过一次同源的坑）。
  正解：`success(...)` 后接 `Promise.resolve().then(断言)`，**一个微任务就够**；
  而且微任务必定排在 `setImmediate` 之前，不会被 `[19]` 链尾的 `process.exit()` 截掉。
  另外桩 `wx` 上要补 `canIUse` —— `prompt()` 用它做版本检查，缺了会走「版本过低」分支。
- **`removeCategory` 的写入顺序是有讲究的：先搬事项、后删分类。** 反过来一旦中途失败，
  事项会连同归属一起变成孤儿；现在最坏也只是「分类还在、事项已搬走」，可以人工恢复。
  「不可逆操作的步骤顺序，应该让中间态是**可修复**的」——这条能推广到所有级联操作。
- **权限设计按「破坏力」分层比按「操作类型」分层更合理。** 同为「删分类」，空分类人人可删，
  非空分类只有创建者能删 —— 因为后者的实际破坏力等同于清空数据。
  一刀切（全开放或全锁死）两边都会让用户别扭。
- **长按 + 点击可以共存**：小程序明确规定绑了 `longpress` 并触发后 `tap` 不再触发。
  这解决了我一开始担心的「破坏性动作要侵占高频手势」的问题 —— 不需要放弃点行切分类。

## 第十四轮 · 体验版发布后的迭代机制（答疑，没改代码）

用户已自行发布成功体验版，问「还能继续迭代吗、改完重传就行了吗」。

### 查到的两条关键事实

1. **体验版迭代无次数限制、不涉及审核**（审核只卡正式版）。
   后台一般会自动把最新上传的开发版本作为体验版（同一开发者上传时）；
   保险起见去「版本管理 → 开发版本 → 选为体验版」点一下，成本为零。

按「改了什么 → 要跑哪条管道」给了一张矩阵表（界面 / 云函数 / action 清单 / 新增集合），

## 第十五轮 · 修 bug：拖动卡顿 + 按住拖不动

用户报「调整顺序拖拽时明显卡顿」「长按时拖不动，要多试很多次才成功」。改 3 个文件（页面 js / wxss / 测试）。

### 根因一（拖不动）：拖动启动的异步竞态

这是真 bug，不是手感问题。`startDrag` 里 `measureRows` 是异步的（过渲染层一个来回，
十几到几十毫秒），而这期间 `_dg` 还是空的 —— `onRowMove` 于是在**每一个 touchmove** 上
再喊一次 `startDrag`：

- `_dragSeq` 被反复自增 → 在途的回调全部对不上号，被当「迟到的僵尸回调」丢掉；
- `dragY` 被反复压回 0，`_dgY0` 被反复改写；
- 每喊一次还附带一次 4 字段的 `setData`。

**手指一直在动、touchmove 不停，回调就永远等不到落地。** 反过来，如果按下后停顿一下
（touchmove 出现间隔 > 一个来回），回调就赢了，卡片能拿起来 —— 这正是用户说的
「要多试很多次才能成功」。

修法：加 `_dgP` 闸，在途期间只认第一次调用；拿到 `_dg` 后自动松开（`onRowStart` /
`endDrag` / 收尾分支 / 测量失败分支都清，防漏清把它永久卡住）。

> **为什么第 9 轮没发现**：`_dragSeq` 是为另一个 bug（僵尸拖动）加的，它解决的是
> 「回调太晚」，而这次的病是「回调永远等不到」。同一个异步窗口，两个相反方向的坑。
> 更要命的是**它只在真机出现** —— 仿真桩默认同步回调，`_dg` 立刻装上，永远复现不了。
> 所以第 22 组必须把测量改成排队（`measureDeferred`）才抓得到。

### 根因二（卡顿）：高频通道没有节流

`applyDragMove` 的高频分支原来是 `this.setData({ dragY: dy })` —— **无条件**推。
对照左滑那条通道，人家有 `if (Math.abs(x - prev) < 5) return;`，这里一个都没有。

而 `dragY` 出现在**每一行**的 `style` 表达式里，每 setData 一次整个列表的样式都要重算。
touchmove 在真机能到 60~120Hz → 每帧一次全列表样式重算，而且大部分是亚像素变化，
屏幕上根本看不出来。

修法：`Math.round` 量化成整数 px + `dg.pushedY` 去重。落点判定也改用这个整数位移 ——
屏幕上就是它，判定基准和渲染必须一致。

### 顺手去掉的一处浪费

`onRowStart` 原来无条件 `setData({ dragging: true })`。`dragging` 唯一的作用是给那一行加
「关掉过渡动画」的类，而它必须与第一帧位移同时到场 —— 在 touchstart 就推，等于
**每次碰卡片（点一下、想滚列表、按手柄）都白触发一次全列表重渲染**。
挪进 `onRowMove` 的位移分支，与 `swipeKey/swipeX` 合成一次 setData。

### 还有一处纯渲染开销

`.row-in.lift` 那圈 `box-shadow` 是 28px 模糊（`0 24rpx 56rpx -18rpx`）。被拖动的卡片
每帧都在挪位置，阴影跟着重绘就是每帧重画十几万像素的高斯模糊。加 `will-change: transform`
让它成为独立图层，移动退化成合成。

> 这和项目已有的「静止的行一律不挂 transform（避免图层爆炸）」是同一条思路的两面：
> 图层很贵，所以只给**真正在动的那一个**用。

### 沉淀

- **修异步 bug 时，要同时问两个方向：「回调太晚」和「回调永远等不到」。**
  `_dragSeq` 防住了前者，反而让后者藏了三轮。加防重入闸时要连**清理路径**一起想清楚
  （`onRowStart` / `endDrag` / 收尾 / 失败分支），漏一条就会把闸永久卡死 ——
  那比原来的 bug 更难查。
- **只在真机出现的 bug，要先把仿真桩改成能复现它**（这次是把同步回调改成排队），
  否则测试跑一万遍也是绿的。这不是「测试没覆盖」，是**桩比真机简单**。
- **性能断言也必须带反向对照**。第 22 组里每一条（闸、量化）都配了「手动拆掉修复，
  同样的操作立刻退化」的对照断言 —— 项目的规矩：不这么写就可能是「写了也永远绿」。
- **`setData` 的代价要看这个字段被多少地方引用**。`dragY` 只有一处引用，但那处在
  `wx:for` 里，于是它等价于「每次 setData 重算整个列表」。凡是要按帧推的字段，
  先数一下它挂在哪。

## 第十六轮 · 提醒推送可行性调研（方案已定，未写代码）

用户问：「我的提醒时间现在有消息推送能力吗，如果增加的话，我希望在时间提醒的前十分钟
收到消息，如果有消息，我的体验版小程序能推送到微信里面吗」。这是调研 + 设计，没动代码。

### 查清的现状

`remindAt` **只存字段**，全项目零推送能力：云函数 17 个 action 没有一个和通知有关，
`cloudfunctions/` 下连 `config.json` 都没有。详情页那个「待提醒」只是本地计数。
README 里「本次不做推送」那句是准确的。

### 三个关键结论

1. **体验版能推送。** 订阅消息是服务端按 AppID + openid 发到用户微信的「服务通知」，
   跟小程序跑哪个版本无关（官方社区有「同一用户同时收到正式版与体验版两条订阅」的实例）。
   唯一要处理的坑是下发接口的 `miniprogramState`：它决定**点击通知后跳哪个版本**，
   默认 `formal` —— 还没发正式版就必须设 `'trial'`，否则跳「该小程序未发布」。
   网上「体验版不支持订阅消息」的说法**判定不可信**：它称「体验版 appid 与正式版不同」，
   而同一小程序的开发/体验/正式本就是同一个 AppID；它混淆的是**旧版模板消息的 formId 限制**
   （基础库 2.10.0+ 禁 formId），那套 2019 年就被订阅消息取代了。

2. **真正卡住的是「个人主体只能用一次性订阅」。** 长期订阅仅对政务民生 / 医疗 / 交通 /
   金融 / 教育等特定二级类目开放。一次性订阅：订阅一次 = 只能下发一条；官方运营专员原话
   「订阅一次下发一次，**订阅次数可以累积**」「**没有时间限制**」。
   但**每一条额度都得用户点一次触发来攒** —— 官方 Q&A：「勾了『总是保持以上选择』≠
   可以随便发，用户没有再次点击触发订阅的按钮就不会增加订阅次数」；勾选之后调用不再弹窗
   但次数照常 +1，所以体感是「点一下保存就静默攒一条」。
   → **「设一次提醒、以后每月都收到」在个人主体下做不到**，这条预期必须先跟用户讲清。

3. **必须新建独立云函数 `fqRemind`，不能塞进 `fqTodo`。** 根因是
   `getWXContext()` 在定时触发器里**没有任何用户上下文**，而 `fqTodo` 的铁律是
   「每个 action 第一步 `ensureFamily(OPENID)`」—— 混进去就是给铁律开例外。
   另外官方文档：一个云函数下只支持一个定时触发器；`config.json` 要**单独「上传触发器」**
   才生效（只「上传并部署」不带触发器，高频坑）。

### 官方文档里四条照抄的事实

| 事实 | 说明 |
|---|---|
| 触发器时区**固定 UTC+8** | cron 直接按北京时间写，不用转 |
| **会重复触发，必须去重** | 原文：「网络环境不稳定，微信可能会多次推送同一条消息。建议将消息 ID 作为唯一标识做好去重」→ `where({_id, pushed:false}).update({pushed:true})`，只有 `stats.updated===1` 那次才真发 |
| cron **七段式** | 秒 分 时 日 月 星期 年；`0 * * * * * *` = 每分钟第 0 秒；最小粒度分钟 |
| 触发器来源判断 | `getWXContext().SOURCE === 'wx_trigger'` |

### 第 16 轮三选（用户已确认，全取推荐项）

1. 额度来源 = **保存带提醒的事项时顺带请求一次授权**（1 条额度换 1 次提醒）。
2. 收件人 = **只发给「设置这条提醒的人」**（不全家广播，否则一条提醒烧两份额度）。
3. 兜底 = **额度不够时在小程序内显示「N 条提醒未送达」**，引导补授权，不静默吞掉。

## 第十七轮 · 模板字段 key 的取法（答疑，未写代码）

用户回传 `templateId = 1AaZ3iSMfGpplGMUIVArXIPssCKAj2p3hHFxJPpOmlM`（模板「待办事项提醒」），
但他截的图是**公共模板库的列表页**，问「字段1：名称=__ key=__ 该怎么填」。**卡点找到了。**

**根因：我把「关键词」和「字段 key」混着说了，没交代它们不在同一屏。**

- 公共模板库**列表页**那一列「关键词」（事项名称 / 事项类型 / 备注消息 / 事项主题 / 提醒时间）
  是**模板的搜索标签**，拿它当 key 赋给代码 → 消息一条都发不出去。
- 真正的字段标识只在**「我的模板」→ 点详情 → 「模板内容」**里，形式是 `{{thing1.DATA}}`；
  **key = 花括号内去掉 `.DATA` 的部分**，名称 = 它对应的中文。

顺带补全的两条（搜索核实的，非官方一手，以模板详情页标注为准）：

| 前缀 | 上限 | 用途 |
|---|---|---|
| `thing` | ≤ 20 字 | 事项名称（超长必须截断） |
| `time` | `YYYY-MM-DD HH:MM` | 提醒时间 |
| `name` / `character_string` / `phrase` | ≤10 / ≤32 / ≤5 | 本项目用不上 |

**勾了几个字段就得赋几个非空值**，少一个整条 47003 —— 所以「事项类型 / 事项主题」用不上的
也得填 `-` 之类兜底。

### 沉淀

- **交接「抄什么」时必须交代「去哪一屏抄、长什么样」，只给一个空表格等于没交接。**
  这次返工一整轮，纯粹因为我说了「字段标识（`thing1` / `time2` 这类）」，却没告诉他
  这些标识在**另一屏**上、而且旁边还并排着一列**长得同样像字段名的中文关键词**。
  **给用户填的表格，旁边要附一行「样例」** —— 一个填好的示例行，比一段描述管用十倍。
- **同名/近名概念要在同一句话里对照着说。** 「关键词」这个词在微信后台里指的是模板的
  搜索标签，而在很多教程里又被拿来指「字段」。用户看到的和我说的不是同一个东西，
  但他没法知道 —— 所以**凡是有歧义的术语，第一次出现就要把两边的叫法都列出来**。

### 云函数 fqRemind 的骨架

`config.json` 声明两件事：`permissions.openapi: ['subscribeMessage.send']`（云调用权限）
和 `triggers: [{type:'timer', config:'0 * * * * * *'}]`（每分钟第 0 秒）。
`index.js` 每分钟跑一遍：**抢锁 → 扣额度 → 下发 → 记结果**。

### 三条「照抄官方事实、别凭记忆改」的硬约束

1. **会重复触发 → 必须抢锁去重。** 官方原文「网络环境不稳定，微信可能会多次推送同一条消息」。
   做法是乐观锁：`where({_id, done:_.neq(true), pushed:_.neq(true)}).update({pushed:true})`，
   只有 `stats.updated === 1` 的那一次才真发。**不需要额外的锁表。**
2. **扫描条件必须带下界**：`remindAt: _.and(_.gt(0), _.lte(t))`，**不能只写 `_.lte`** ——
   `remindAt` 为 `null` 的文档在 `$lte` 下也会被捞出来（null 在类型序里排在数字之前），
   白占分页窗口。第 [4] 组钉这条。
3. **`pushed` 的排除必须写 `_.neq(true)` 而不是等值 `false`。** 升级上来的老文档压根没有
   这个字段，等值条件挑不到它们 → 那批提醒**永远发不出去、而且一点报错都没有**。
   第 [4] 组专门放了一条「删掉 `pushed` 字段的老事项」的用例。

时间格式化写死 +8 偏移再取 `getUTC*`，不信任容器时区；第 [8] 组拿 ICU 时区库算出的北京时间
做对照，并反向断言「它不是 UTC 裸值」—— **同一套算法自证没有意义。**

### 自己加的三个设计（官方没要求，但缺了会难受）

| 设计 | 为什么 |
|---|---|
| 迟到 5 分钟内补发，超过记 `expired` | 容器冷启动 / 触发器漏跑都会过点。补发几小时前的提醒只会让人困惑；但也不能静默丢弃 —— 记成「未送达」让用户看得见 |
| 扣不到额度时**仍然标记 `pushed`** | 否则每分钟重试到天荒地老。代价是补了额度也不补发（那条时间已经过去了） |

### 沉淀

- **定时任务的三件套：抢锁去重、窗口加下界、老字段用 `neq`。** 三者缺任何一个都是
  「静默不发」或「重复发」，而且都不报错 —— 这类 bug 只能靠测试钉。
- **平台字段的「不存在」和「false」是两回事。** 任何给集合后加布尔字段的场景
  （`pushed` / `deleted` / `synced`），过滤条件一律用 `_.neq(true)`，等值判断会漏掉老数据。
- **`setData` 之外还有一条纪律：测试里不要缓存「会被整体替换」的对象引用。**
- **失败不退还额度是明知取舍**：微信那边其实已经消耗掉了，退了记账反而不准。README
  的取舍表写明了。同理「补了额度也不补发过去了的提醒」。
- **新增 action / 新增集合都要走发布管道**：`ACTIONS` 从 17 → 18 → 两端 `FN_VER` 4→5；
  `fqRemind` 除「上传并部署」还要**单独点一次「上传触发器」**（只上传并部署不带定时触发器，
  表现为「提醒永远不发、而且一点报错都没有」）。
