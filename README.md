# 四象限事项待办中心 · 微信小程序

基于艾森豪威尔矩阵的待办应用。移动端重构自 PC 版功能，视觉调性为「作战指挥」：
四象限以满色块呈现，用饱和度和面积换取「今天该打哪一仗」的即时判断力；
下钻到详情后自动降压为白底列表，把注意力交还给具体事项。

- 设计稿：`four-quadrant-mobile`（4 屏 + 设计规范 + PC→移动端功能映射表）
- 技术栈：微信原生小程序 + 云开发（云函数 + 云数据库）
- 数据存储：云数据库，按 `openid` 隔离，多端同步

---

## 一、跑起来

### 1. 建六个集合

微信开发者工具 → 云开发 → 数据库 → 新建集合：

| 集合名 | 用途 |
|---|---|
| `fq_family` | 家庭（一份共享清单 = 一个家庭）；存家庭名、创建者、邀请码、数据版本号 `rev` |
| `fq_members` | 家庭成员关系（谁在哪个家庭里、什么身份、当前是不是活跃家庭） |
| `fq_categories` | 分类（工作 / 生活 / 自建） |
| `fq_items` | 事项 |
| `fq_subs` | 提醒推送额度（**每人一条**：攒了几条、还能发几条） |
| `fq_plans` | 日程计划（**每人一条/每天一条**：今天要做什么、明天准备做什么） |

六个集合的**权限都设为「仅创建者可读写」**。
客户端不直接读数据库，所有读写都走云函数；这条规则是防止有人绕过云函数直连。

> ⚠️ 「仅创建者可读写」对云函数**不起作用** —— 云函数用的是管理员权限，会绕过安全规则。
> 所以**真正的越权防线在云函数代码里**：归属键 `fid` 只能由服务端从 `OPENID` 推导
> （见 `ensureFamily`），绝不接受客户端传入。这条在 §十一 有专门说明。

### 2. 部署云函数

有两个云函数，**都要部署**：

| 云函数 | 怎么部署 | 说明 |
|---|---|---|
| `fqTodo` | 右键 → **上传并部署：云端安装依赖** | 唯一数据出口，全部读写都走它 |
| `fqRemind` | 同上，**外加右键 → 「上传触发器」** | 提醒推送。只「上传并部署」**不会带上 `config.json` 里的定时触发器** —— 后果是提醒永远不发，而且一点报错都没有。这是这个功能最容易漏的一步 |

（部署前确认各自的 `package.json` 里的 `wx-server-sdk` 依赖已随包上传。）
`fqRemind/config.json` 里有两样东西不能少：`permissions.openapi` 里的
`subscribeMessage.send`（云调用权限，缺了发送直接没权限），以及每分钟跑一次的 `triggers`。

> ⚠️ **「编译」永远不会上传云函数。** 这是本项目最容易踩的一个坑：
> 改了 `cloudfunctions/fqTodo/index.js` 却只点「编译」，小程序端跑的是新代码、
> 云端跑的还是旧包，于是报出一堆看不懂的错（典型的是拖动排序落库时
> `未知 action: reorder`——旧包里根本没有这个 action）。
> **只要动过云函数，就必须重新上传部署一次。**

#### 版本握手（防这个坑的第二道闸）

`cloudfunctions/fqTodo/index.js` 和 `miniprogram/utils/const.js` 里各有一份
`FN_VER`（当前 **8**），必须**始终相等**。云函数 `bootstrap` 会把 `fnVer` 和
`actions` 清单一起返回，小程序首屏拿它对一下：

- 版本一致 → 静默；
- 云端没上报 `fnVer`（说明是旧包）或版本不等 → 首屏直接弹窗
  「云函数版本过旧」，并写明「右键 fqTodo → 上传并部署」的步骤。

**约定：只要改动云函数的 action 清单（新增 / 删除 / 改签名），两边 `FN_VER` 一起 +1。**
只改一边的话握手就白做了——`test-reorder.js` 第 [17] 组会读两份源码比对，漏改会红。

> ⚠️ **没有新增 action 也要 +1。** 版本号钉的是「云端认不认得客户端发过来的字段」，
> 不只是 action 清单。`v7` 就是这么来的：进度条一个 action 都没加，但旧云函数不认识
> `progress`（白名单写法会把它悄悄丢掉），客户端拖完看着生效、一刷新全回 0% ——
> 又是一次「拖了才知道」的静默故障，正是握手要提前拦住的那一类。

> v2 → v3：引入共享家庭，归属键从 `_openid` 变成 `fid`。
> v3 → v4：分类支持删除与改名，新增 `removeCategory` / `renameCategory`。
> v4 → v5：提醒推送，新增 `grantSub`（攒订阅额度）；`fq_items` 多出 `pushed` 系列字段，
> 由独立的 `fqRemind` 定时云函数消费。
> v5 → v6：日程版块，新增 `savePlan`；`bootstrap` / `sync` 多回一个 `plans` 字段。
> v6 → v7：事项进度条。`fq_items` 多出 `progress`（0~100），`updateItem` 里多了
> 「`done` ⟺ `progress === 100`」这条耦合 —— 两者不是两个状态，是同一条状态线的两种读法。
> v7 → v8：可配置的提前提醒时长。`fq_items` 多出 `leadMin` / `pushAt` **一对**字段，
> 推送的扫描条件从 `remindAt` 换成 `pushAt`。
> ⚠️ **那次 `fqRemind` 不重新部署，存量提醒会一条都不发** —— 而 `fqRemind` 不在 action
> 清单里，握手管不到它，只能靠这里的说明提醒自己（见 §十二）。

### 3. 确认环境 ID

`miniprogram/app.js` 里的 `env` 必须是当前云开发环境 ID：

```js
env: "cloud1-d0gaaaa6g7f0f1b61",
```

首次进入会自动写入种子数据（`工作` / `生活` 两个分类 + 5 条示例事项），
打开就能看到矩阵填满的效果。

### 4. 跑不起来？对照这张表

「编译」只处理小程序端代码，**不会上传云函数**。所以最容易卡住的就是下面这几类报错：

| 模拟器提示 | 原因 | 解决 |
|---|---|---|
| `云函数 fqTodo 尚未部署` | 云函数还只是本地文件，云端没有 | 展开 `cloudfunctions` 目录，右键 `fqTodo` → **上传并部署：云端安装依赖** |
| **`未知 action: reorder`**（拖动排序落库时弹出） | 「云端是旧包」：本地云函数已经加了 `reorder`，但没重新上传部署 | 同样是一次**上传并部署**就好。**代码本身没问题**——`test-cloudfn.js` 会拿着假数据库真跑一遍 `fqTodo/index.js`，它绿了就说明问题只在部署 |
| 首屏弹窗「云函数版本过旧」 | 版本握手发现云端 `fnVer` 缺失或与本地 `FN_VER` 不等，即云函数没重新部署 | 同上。这是**主动预警**，比等你拖一次列表才发现要早 |
| `云开发环境不存在，请检查 app.js 的 env` | `app.js` 的 env 与实际环境 ID 不符（换过环境或换过账号） | 云开发控制台复制环境 ID，覆盖 `app.js` 的 `env` |
| `collection not exists` / 提示集合不存在 | 集合没建全 | 云开发 → 数据库 → 新建缺的那个（§一.1 列了全部六个；只做日程的话至少要 `fq_plans`） |

> 分辨「云函数是旧包」还是「云函数代码本身写错了」：跑
> `node .workbuddy/tools/check-all.js`。里面的 `test-cloudfn.js` 会在本地把
> `fqTodo/index.js` 完整跑一遍（含 `reorder`、越权隔离、种子数据、握手字段），
> 它通过就说明代码是对的，剩下的只是部署动作。

补充两点：

- 如果右键 `fqTodo` **看不到「上传并部署」菜单**，说明开发者工具还没关联上云环境：
  先点顶部工具栏的「云开发」按钮开通/进入环境，返回后 `cloudfunctions` 下的函数目录
  图标会变成云朵样式，右键才有部署菜单。
- 部署时选「**云端安装依赖**」，本地不要留 `node_modules`。`fqTodo/package.json` 里
  已声明 `wx-server-sdk`，云端会自己装。

### 组件分层

宿主页 `pages/index` 只留骨架、事项卡片、底部抽屉；其余展示块拆成
`components/<name>/<name>.{wxml,wxss,js,json}`。每个组件都带两个选项：

```js
Component({
  options: {
    virtualHost: true,               // 组件不产生额外节点（必需，不是优化）
    styleIsolation: 'apply-shared',  // app.wxss 的共享资产能进组件
  },
  properties: { /* 数据只从这里进 */ },
  methods: { /* 交互只用 triggerEvent 出去 */ },
});
```

- **`virtualHost: true` 是必需的**：`.screen` 是纵向 flex，各固定块靠 `flex: 0 0 auto`
  占住自己的高度；组件一旦产生真实节点就多出一个 flex item，整套布局开始靠运气。
- **`apply-shared`** 让 `app.wxss` 的共享资产（自绘图标 `.ico-*`、象限图标 `.qmark`、
  通用按钮 `.btn*`）进得来。官方文档原话：「除继承样式外，`app.wxss` 中的样式、
  组件所在页面的样式对自定义组件无效（除非更改组件样式隔离选项）」——
  实测确认：底栏图标只定义在 `app.wxss`，在组件里正常渲染。
- **数据只走 `properties`，交互只走 `triggerEvent`**。组件不碰 `wx.cloud`、
  不读写页面实例 —— 这样它才能被单独看懂。
- **组件内部 handler 保留页面原来的方法名**。WXML 是逐字搬来的（连
  `bindtap="onX"` 一起），js 是手写的，两边名字没有任何东西保证一致，而且
  **完全不报错** —— 一次批量抽取曾造出 5 个「点了没反应」的按钮。所以对外的事件名
  另取（`triggerEvent('pick')`），组件内部沿用原名。这条由 `event-check.js` 守着。

**组件化会造出四类静默故障**（全部不报错，且 arch-check 与逻辑仿真都看不见）：

| 故障 | 现象 | 守卫 |
|---|---|---|
| WXML 里的方法名与 js 对不上 | **按钮点了没反应** | `event-check` A / B |
| 页面 `bind:x` 与组件 `triggerEvent` 不闭合、或取值形状不对 | 按钮没反应 / 拿到 `undefined` | `event-check` C / D |
| 标签没注册 / 切片把标签切坏 | **一整个区块安静地变空白** | `component-audit` |
| 新增组件目录后开发者工具只重编译了一半 | 也是整块空白，但磁盘上查不出任何问题 | 全量「编译」(Ctrl+B) → 清缓存 → 重启工具 |

> 结论：**每加一层间接 / 一类文件，都要问「哪条既有检查现在成了盲区」。**

## 三、数据模型

> **归属键是 `fid`，不是 `_openid`。** `_openid` 现在的含义是「谁创建的」（审计用），
> 所有查询与写入都按 `fid` 过滤 —— 这是共享家庭的地基，详见 §十一。

### `fq_family`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 即 `fid`，同时是 `fq_items` / `fq_categories` 的归属键 |
| `name` | string | 家庭名，≤ 16 字，默认「我的家庭」 |
| `ownerOpenid` | string | 创建者。只有他能改名 / 清空全家 / 生成邀请码 |
| `inviteCode` | string | 6 位邀请码，**只回给创建者** |
| `inviteExpire` | number | 邀请码到期毫秒时间戳（24 小时） |
| `rev` | number | **数据版本号**，每写一次 +1。客户端轮询它判断「家人有没有改过」 |
| `createdAt` | date | |

### `fq_members`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_openid` | string | 成员本人 |
| `fid` | string | 所属家庭 |
| `role` | string | `owner` / `member` |
| `name` | string | 在这个家庭里的显示名（自己填的，不碰任何隐私接口） |
| `active` | boolean | 是不是「当前家庭」。一个人可以入多个家庭，但只有一条为 `true` |
| `joinedAt` | date | |

### `fq_categories`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成，事项通过 `catId` 引用 |
| `fid` | string | **归属家庭** —— 所有读写都按它过滤 |
| `_openid` | string | 谁创建的（审计用，不参与过滤） |
| `name` | string | 分类名，≤ 12 字 |
| `order` | number | 排序 |
| `createdAt` | date | |

### `fq_items`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | |
| `fid` | string | **归属家庭** —— 所有读写都按它过滤 |
| `_openid` | string | 谁创建的（审计用，不参与过滤） |
| `title` | string | 事项标题，≤ 60 字 |
| `note` | string | 备注，≤ 200 字 |
| `quad` | string | `q1` / `q2` / `q3` / `q4` |
| `catId` | string | 所属分类 `_id` |
| `priority` | number | 1–4，对应卡片上的 P1–P4 标签 |
| `done` | boolean | **永远等价于 `progress === 100`**，见下面的耦合说明 |
| `doneBy` | string | 谁勾掉的（openid）。共享清单里「谁完成的」是刚需，顺手就记了 |
| `progress` | number | 完成进度 0–100 的整数。**和 `done` 是同一条状态线的两种读法**，不是两份数据 |
| `remindAt` | number \| null | 提醒时间的毫秒时间戳。**它只是「提前量」的输入**，不再直接决定何时推送（v8 起），详见 §十二 |
| `leadMin` | number \| null | **提前多少分钟提醒**（v8 新增）。白名单见 `LEAD_ALLOWED`，**`-1` = 「不提醒」**。只在有 `remindAt` 时才有值，否则是 `null` —— 没有提醒时间就谈不上「提前多久」 |
| `pushAt` | number \| null | **预算好的推送时刻** = `remindAt - leadMin × 60000`（v8 新增）。`leadMin === -1` 或没设提醒时间时落 `null`。`fqRemind` 只按它扫 |
| `pushed` | boolean | 这条提醒**已经被定时任务处理过**（不论发没发出去）。去重全靠它 |
| `pushedAt` | date \| null | 处理时间 |
| `pushOk` | boolean | 是否真的发出去了。`pushed && !pushOk` = 未送达，我的页会显示出来 |
| `pushErr` | string | 失败原因（`no-quota` / `expired` / 微信错误码），排查用 |
| `order` | number | 排序。种子 1000+，新建用 `Date.now()`（天然排到末尾）；一经拖动即整段重写成 `0 / 10 / 20…` |
| `createdAt` / `updatedAt` / `doneAt` | date | |

**`done` 与 `progress` 为什么必须耦合**：界面上它们是同一根进度条的两种读法 ——
拖到 100% 就是完成，从 100% 拖回来就是自动撤销。如果放任两者各写各的，就会出现
「满格的卡片不算完成」「已完成的卡片显示 37%」这类谁也解释不通的状态，而且
**两边都不会报错**。所以耦合钉在云函数的 `updateItem` 里，客户端说了不算：

- 只传 `progress` → `done` 由它推（`progress >= 100`）；
- 只传 `done` → `progress` 由它补齐（`true` → 100，`false` → 0）；
- 两个都传且互相矛盾 → **以 `done` 为准**，`progress` 被纠正成 100 / 0；
- 落库时统一修正：`done` 为真则 `progress` 落 100，否则落被夹到 0–99 的 `progress`。

`bulk` 的 `markAllDone` 走的是批量路径，同样要写 `progress: 100` ——
这是最容易漏的一个口子（漏了就会出现一批「已完成但进度 0%」的行）。

**客户端的分工**：`patch` 里**只送一个**字段，不送一对。左滑「完成 / 撤销」只送
`{ done }`（进度由云函数补），拖进度条只送 `{ progress }`（`done` 由云函数推）。
两个都送 = 两个真相来源，迟早对不上。

**`pushAt` 为什么要落库，而不是查询时现算**（v8）：提前量是**每条各带一个**的，
所以「该发的时刻」之间毫无关系 —— A 条提前 5 分钟、B 条提前 7 天，一个
`remindAt <= now + 常量` 的单一窗口表达不了这件事。看似可行的替代是把窗口放宽到
最大档（30 天）再在内存里逐条算 `pushAt` 过滤，但 `fqRemind` 的拉取有上限
（`CAP = 500`）：未来 30 天内若超过 500 条待推事项，排在后面的会被**静默丢弃**。
落成 `pushAt` 之后扫描条件回到单一的 `pushAt <= now`，语义与索引都干净，
代价只是每次 `remindAt` / `leadMin` 变化时重算一次。

**`remindAt` / `leadMin` / `pushAt` 三个字段是一组**：`pushAt` 完全由前两个决定，
所以 `updateItem` 里只要 `remindAt` 或 `leadMin` 任一进来，三个就一起重算
（分开更新必然算出个中间态）；且**「提前量真的变了」也要复位 `pushed`**，
否则改完提前量那条提醒永远不再排队（表现是「改了没用」，且不报错）。

⚠️ **`-1` 是「不提醒」的哨兵值，不是「提前 0 分钟」。** 因为 `toLead()` 会把白名单
之外的值一律回落到默认档，若 `0` 是个合法档位，一个脏值（老数据的 `null`、手滑传的
字符串）就会把这条提醒**悄悄关掉** —— 用户以为提醒开着、实际永远不发，这是最糟的
失败方向。用 `-1` 之后 `0` 不在白名单里，脏值只会回落到「提前 30 分钟」，
失败方向变成「发得比预期早」，用户看得见、也改得回来。

**排序为什么是「整段重写 0/10/20…」**：拖动只改相对顺序，用「相邻两条取中值」会一路把
浮点间距耗光，几十次拖动后 collapse 就得做重排；整段重写虽然多写几条，但结果确定、
人工在控制台里也一眼看得懂。客户端只提交**真正变了 order 的那些行**，
所以一次拖动通常只写 3 条左右。

**排序粒度是「象限 × 分类」**：重排只影响当前分类下、同一个象限里的事项。
别的分类（甚至别的象限）即使 order 撞值也不影响显示，因为它们从不会同时出现在一个列表里。

### `fq_subs`

提醒推送的额度账本 —— 全项目唯一一张**按人**而不是按家庭归属的表。

| 字段 | 类型 | 说明 |
|---|---|---|
| `_openid` | string | 谁攒的额度。提醒发给的是条目创建者，额度也就一人一份 |
| `quota` | number | 还剩几条能发，上限 50（`MAX_QUOTA`） |
| `lastGrantAt` | number | 上次记账的毫秒时间戳，用来拦脚本连点（300ms 内只算一次） |
| `updatedAt` | date | |

为什么额度不是家庭资产：微信的一次性订阅是**按用户授权**的，一个人点「允许」只买到
他自己的一条发送权。详见 §十二。

### `fq_plans`

日程计划 —— 第三张**按人**归属的表（前两张是 `fq_members` 与 `fq_subs`）。
「今天要做什么 / 明天准备做什么」是自己写下的笔记，不是家庭资产。

| 字段 | 类型 | 说明 |
|---|---|---|
| `fid` | string | 归属家庭。和其它 action 一样**由服务端推导**，不接受客户端传入 |
| `_openid` | string | 谁写的。**同一个家庭里两位成员写同一天，必须是两条记录** |
| `date` | string | `YYYY-MM-DD`。**字符级严格校验**：它是唯一键的一部分 |
| `text` | string | 计划正文，上限 300 字（云函数 `MAX_PLAN` ↔ 客户端 `PLAN_MAX`，成对常量） |
| `updatedAt` | date | |

唯一键是 `(fid, _openid, date)`，写入是 upsert；**空文本 = 删除这一天**（所以界面上没有单独的删除按钮：
清空再保存就是删除）。服务端把日期键校验到字符级，是因为放过 `2026-10-9` 这种写法就会在「同一天」存出两条。

为什么按人而不按家庭：读取时（`plansFor`）**必须带 `_openid` 过滤**，否则你会在自己的日程里看到
家人写的计划，两边还会用同一个日期键互相覆盖。`clearAll` 也只清**调用者自己**的那份 ——
创建者有权清空全家的事项，没权删家人写下的日记。

**建议索引**：`fq_items` 建复合索引 `fid(升) + order(升)`；`fq_categories` 建 `fid(升) + order(升)`；
`fq_members` 建 `_openid(升) + active(升)`（每次 action 都要靠它解析当前家庭）与 `fid(升)`；
`fq_family` 建 `inviteCode(升)`（按码找家庭）；`fq_subs` 建 `_openid(升)`；
`fq_plans` 建 `fid(升) + _openid(升) + date(升)`（三个字段合起来才是唯一键，upsert 直接查它）；
`fq_items` 另建 `pushAt(升) + pushed(升) + done(升)`（`fqRemind` 每分钟按这三个字段扫一次）。
> ⚠️ **v8 之前这里写的是 `remindAt`**。升级时务必改建这条索引 —— 扫描条件已经换成
> `pushAt`，索引还留在 `remindAt` 上不会报错，只是每分钟全表扫一遍。

## 四、云函数接口

单一入口 `fqTodo`，用 `action` 分发。每个 action 的第一步都是 `ensureFamily(OPENID)`
—— 解析出「调用者当前属于哪个家庭」，之后所有读写都按这个 `fid`。
入参一律做类型收敛与长度截断，分类归属会二次校验，返回 `{ ok, data | msg }`。

| action | 入参 | 说明 |
|---|---|---|
| `bootstrap` | — | 首次自动建默认家庭 + 种子；返回 `{ categories, items, family, sub, fnVer, actions }`（分页取全，上限 500）。后两个是握手字段，客户端只用来判断云端是不是旧包 |
| `sync` | `rev` | **自动同步**。rev 与云端一致 → `{ changed:false, rev }`（几十字节）；不一致 → 顺带把整份数据带回来（含 `sub`：额度可能刚被定时任务消耗掉） |
| `addItem` | `item{title,note,quad,catId,priority,remindAt,leadMin}` | 新建事项的 `progress` 固定落 `0`（不接受客户端指定，避免一建出来就是「八成完成」）。`leadMin` 只在 `remindAt` 非空时采纳，并顺手把 `pushAt` 算好落库 |
| `updateItem` | `id, patch{...}` | `patch.done` / `patch.progress` **任一个进来都会同时定下另一个**：`done ⟺ progress === 100`。`patch.done` 还会同步维护 `doneAt` 与 `doneBy`；`progress` 一律夹到 0–100 取整。`patch.remindAt` / `patch.leadMin` **任一进来就把 `remindAt` / `leadMin` / `pushAt` 三个一起重算**，且与旧值不同时复位 `pushed` / `pushedAt` / `pushOk` / `pushErr`（只改标题不会误触发） |
| `removeItem` | `id` | |
| `reorder` | `items[{id, order, quad?}]` | 拖动排序 / 跨象限移动。逐条校验 `fid` 归属，单次上限 200 条；`quad` 不传则只改顺序 |
| `bulk` | `op, quad, catId` | `op`: `markAllDone` / `clearDone` / `clearQuad`。`markAllDone` 会一并把 `progress` 写成 100（批量路径同样受那条耦合约束） |
| `clearDone` | `catId`（可选） | 我的页「清空已完成」，不传则跨分类 |
| `clearAll` | — | 我的页「清空全家数据」，分类保留。**仅家庭创建者**。日程计划只清**调用者自己**的那份 |
| `savePlan` | `date, text` | 日程计划 upsert。`date` 必须是 `YYYY-MM-DD`；**空文本 = 删除这一天**；内容没变则不写（不让 `rev` 白涨） |
| `addCategory` | `name` | 重名会被拒 |
| `removeCategory` | `id, moveTo?` | 删除分类。带 `moveTo` = 先把该分类下的事项搬过去再删；不带 = 连事项一起删。**空分类谁都能删；非空分类仅家庭创建者**。家里至少要留一个分类 |
| `renameCategory` | `id, name` | 改分类名，同家庭内重名会被拒（改成自己原来的名字不算重名） |
| `genInvite` | — | 生成 / 刷新邀请码。**仅创建者** |
| `joinFamily` | `code` | 用邀请码加入对方的家庭（切换当前家庭，不动任何数据）。大小写与空格会归一化 |
| `leaveFamily` | — | 退出当前家庭，回到自己那份。创建者不能退自己的家 |
| `renameMember` | `name` | 改自己在家庭里的显示名，≤ 12 字 |
| `renameFamily` | `name` | 改家庭名。**仅创建者** |
| `grantSub` | `templateId` | 攒一条提醒推送额度。`templateId` 必须等于本项目模板（客户端从 `bootstrap` 拿到后回传）；加多少由服务端定，总量封顶 50。返回 `{ quota, capped, tooFast }` |

`sub` 的形状是 `{ quota, missed, templateId }`：还能发几条、有几条到点了没发出去、模板 id。
**模板 id 只由服务端下发，客户端不硬编码一份** —— 换模板时只要改云函数那一处。

> - 验「检查器有没有先剥注释」这类改动，**正/反向要成对做**：只把守卫删掉、却不在源码里
>   放一条含插值/类名的注释，会得到一个**假的绿**（源码里本就没有地雷）；
> - 反向对照还能定位「守卫住哪一层」：`arch-check` 的注释其实是 `wxml-flatten.js` 摊平时剥的，
>   在 `classTokens` 里重复剥一遍纯属装饰。

### 1. 静态契约（mp-check）

```bash
node .workbuddy/tools/mp-check.js \
  miniprogram/pages/index miniprogram/components miniprogram/app.wxss
```

参数可以传文件，也可以传目录（目录会递归展开其中的 `.wxml` / `.wxss` / `.js`），混着传也行。
组件化之后**不要再往里硬编码文件路径** —— 进化的方式是「多一个组件目录」，
逐条列路径迟早会漏，而漏掉的那个正好就是契约的盲区。

四件事：

1. **class 契约** —— WXML 用到的 class 是否都在 WXSS 里有规则（**全局**看：组件是 `apply-shared`，页面样式本来就进得去）
2. **data 契约** —— WXML 插值里引用的根变量是否都在同作用域的 `Page.data` / `Component.properties` 里声明（**按目录分作用域**：组件看不见页面的 data，页面也看不见组件的 properties）
3. **结构配对** —— `{}` `()` `{{}}` 与标签闭合
4. **固定头部** —— `dhead` / `filters` / `sortrow` 不得出现在 `<scroll-view class="scroller">` 里面

第 4 条是给「头部固定」这条约定兜底的。头部若被写回滚动区，WXML 依然完全合法，
任何语法检查都发现不了 —— 只在列表变长后表现为「滑到底部找不到返回键、够不着『调整顺序』」。
反向用例验过：把 `sortrow` 塞回滚动区，它准点报出 + 退出码 1。

退出码非 0 表示有需要人工确认的项。

### 2. class 重名扫描

```bash
node .workbuddy/tools/class-collision.js \
  miniprogram/pages/index/index.wxml \
```

只用前者会误报一片（`.btn .ico-plus`、`.row.done .row-in` 这类「元素自身 + 修饰上下文」是正常写法）。

**拖动上手体验**（起点连续 `touchmove` 时 `startDrag` 只许真正执行一次、位移原点不被覆盖、

离开边缘立刻收手、滚到底不对着墙反复 `setData`、松手一定停表）、
**自动同步的避让规则**（空闲时会拉；排序模式中、编辑抽屉开着时、本地还有没落库的写操作时
一律不发请求 —— 第三条正是「点一下界面闪回去」的正源。做法是把一次写操作挂起不 resolve，
制造「在路上」的真实状态，再验证落库之后同步恢复、`stopSync` 之后彻底停）、
**家庭视图层约定**（只有创建者能看到「清空全家数据」和「生成邀请码」、只有成员能看到「退出家庭」、
成员行用服务端给的 key、**客户端没有任何一处把 `fid` 当参数发给云函数**、分享卡片必须带邀请码）、
**分类管理的交互契约**（长按才出面板、点行仍是切分类；面板记的是**被长按的那一行**而不是当前选中的分类；
空分类一次确认就删、非空分类先进「选事项新家」那一步；级联删除必须二次确认且文案点明家人的条目也在其中；
成员遇到非空分类时请求和确认框都不产出；只剩一个分类时连确认框都不弹；
删掉的正好是当前分类时 `state.catId` 必须自动回落 —— 不回落整页就是一片空白；
改名走可输入弹窗、名字没改就不白发请求）、
**提醒推送的客户端契约**（客户端不硬编码模板 id；弹授权的地方**全文件只有一处**、只在保存
带提醒的事项时请求、且排在 `closeSheet` 之后落库之前 —— `requestSubscribeMessage` 必须在
用户交互的那次调用栈里；只有 `accept` 才算攒到额度；`grantSub` 占住同步避让名额；
我的页的「未送达」入口只在有未送达时出现、点了会给解释；`adoptSub` 对负数 / 脏值 /
缺字段都要收敛而不是崩）、
**事项进度条的读写口径与手势契约**（`rowVM` 读的 `pct` 对没有 `progress` 的老数据要回落成
「完成？100 : 0」，而不是 `undefined`；「点一下圆点跳过去」这条路走 `onProgEnd`，
而它在落库前会先把手势状态清掉 —— 所以百分比换算必须由**调用方把 rect 传进去**，
自己去读 `this._pg` 会整条静默失效：不报错、不落库、进度不动；
拖动过程中只走**单行路径 setData**（`rows[i].pct` / `sections[j].rows[i].pct`），
不许 `render()` 整页重绘；两个视图落在**两棵不同的数据树**上，`progPath` 只看当前视图那一棵；
纵滑（`|dx| <= |dy|`）必须永久放弃这一次手势，免得「先往下滑再往右滑」把列表滚动掰成改进度；
排序模式下不响应触摸但**照旧 catch 掉事件**，所以也不会误触发卡片左滑）、
**提前量的本地镜像**（抽屉重开读的是 `item.leadMin`，而落库是异步的 —— 镜像漏写不会报错，
表现是「刚选的提前量，重开一次就变回默认档」，**与「云端还是旧包」那个故障长得一模一样**，
所以这条断言的价值不只是守住乐观更新，更是把两个成因分开；新建那条路的镜像是写在
promise 的 `then` 里的，只能靠静态断言守 —— 本文件的结算点在 [19] 的链尾，
写在 `then` 里的断言根本轮不到执行，那会是一条**假装在测**的断言）。

补齐而不是落 `null`）。

> 它红了，才是代码本身要改。

### 5. 提醒推送逻辑仿真测试（fqRemind）

`fqRemind` 跑在**定时触发器**里，本地没法手动触发，而它出错的方式全是静默的：
去重失效会重复推送（每次还都烧掉一条攒来的额度）、窗口条件写松会把几个月前的老提醒
补发一遍、额度判断写反会「扣了不发」或「发了不扣」。所以在同一个假云 SDK 上真跑一遍。

```bash

```

覆盖 14 组、129 条断言：到点的一条扣 1 条额度、发 1 条、结果落库（收件人 = 条目创建者、
`miniprogramState` 必须是 `trial`）、**去重**（同一轮重复跑，以及两个实例 `Promise.all`
并发，合计都只发 1 条 —— 判别力来自「第二轮必须一条候选都扫不到」）、
**额度不足**（不发、记 `no-quota`、仍然标记已处理以免变成每分钟重试的漩涡、补了额度也不补发）、
三类不该发的（已完成 / 还没进 10 分钟窗口 / 压根没有提醒时间）、

**窗口边界**（刚过 1 分钟补发、过 10 分钟记 `expired` 不补）、

**按 `pushAt` 扫描**（到期判据、排序、以及「三份白名单逐字相同 / 默认提前量三处都是 30」的
跨文件比对）、**老数据回填**（没有 `leadMin` / `pushAt` 的老文档第一轮就被补上默认提前量，
补完的第二轮挑不到它们；而「不提醒」的条目 `pushAt` 是 `null`，既不被回填也不进候选 ——
判据是 `leadMin` 缺失而不是 `pushAt` 缺失，选后者会**反复扫到同一条、无限回填**）。

> 这组测试还做过两轮**变异验证**：早期把抢锁、额度检查、窗口条件、时区换算、`trial` 标记、
> 槽位赋值等 10 处关键判断逐个改坏；v8 又对提前量做了一轮 **19 条**（含 1 条对照组），
> 确认每一处该红的都红、对照组保持绿。
> 一份永远绿的测试和没有测试是一样的。
>
> ⚠️ v8 那轮里有一条变异**本来就被删掉了**：「回填判据从 `leadMin` 换成 `pushAt`」跑出来
> 是绿的，查证后发现它**本来就区分不了** —— 判据只影响「挑哪些文档」，而新数据的两个字段
> 都在、老数据的两个字段都缺，两种判据挑出的是同一批文档；差异只出现在「值为 `null` 的字段
> 会不会被容器当成缺失」这种平台行为上，那不是本地假 SDK 能如实模拟的东西。
> 与其留一条永远绿的假守卫，不如把结论写进注释：用 `leadMin` 作判据是**更严谨**的选择
> （它和 `pushAt` 同生同灭，不受空值语义影响），但**别声称测试守住了它**。

## 七、手势与排序模式

| 手势 | 结果 |
|---|---|
| 横向滑动卡片（非排序模式） | 左滑露出 2 个操作（240rpx）：未完成 → 完成 / 删除；已完成 → 撤销 / 删除。**位移不到 45% 阈值就整个收回**，不留半个面板 |
| 横向拖动卡片**底部的进度条**（非排序模式） | 圆点跟手走，**松手才落库**；拖到 100% 即完成，从 100% 拖回来自动撤销。**按住轨道任意位置点一下**，圆点直接跳过去（不必先精确按住那个 30rpx 的小圆点） |
| 点卡片（非排序模式） | 进编辑抽屉；若该行正滑开着，这一下只收起，不进抽屉 |
| 点「调整顺序」 | 进排序模式：只允许**拖手柄**，其他按钮全部锁住；列表本身照常滚动。同时 `wx.vibrateShort` + 卡片整体抖一下，作为「已进入可拖状态」的一次性信号 |
| 按住卡片**右侧手柄**拖动（仅排序模式） | 纵向移动即换位，松手落库。拿起和拖动**都不再抖动/震动** |
| 在卡片**本体**上纵向滑动（仅排序模式） | 就是滚列表，和平时完全一样 |

**进度条为什么能同时和「左滑」「滚列表」共存**：卡片上一下子有了三处手势，其中
左滑和拖进度**都是横向**的 —— 而横向手势只会判给先到的那一方，所以不能靠
「谁先响应」，只能靠**指定胜者**。做法与拖动手柄（`.dh`）完全一样，是同一套手法的第二次应用：

| 事件 | 挂法 | 为什么 |
|---|---|---|
| `touchstart` | **`catch`** | 截住手势，`.row-in` 的 `onRowStart` 收不到 → 左滑从第一帧起就没启动 |
| `tap` | **`catch`** | 吸掉点击，否则「点一下改进度」会顺带弹出编辑抽屉（`onProgTap` 是**有意为空**的事件屏障，不是忘了实现） |
| `touchmove` | **`bind`** | 横滑才吃这串手势；纵滑原样放过给 `scroll-view` |

⚠️ `touchmove` 必须是 `bind`。若这里也 `catch`，每张卡片底部就会多出一条 48rpx 高、
**按着滑不动的死区** —— 长列表里非常难受。（顺带也证明了 `catchtouchstart` 不会挡住
`scroll-view` 自己滚动：真要挡滚动，社区里就不必到处用 `catchtouchmove` 了。）

共享进度条那段 CSS 同理**刻意不写 `touch-action: none`**：它是「别把这串 touch 判成页面滚动」
的第二道保险，代价是那一块区域再也滚不动。饮水卡挂在总览页（整页本来就不滚）上无所谓，
事项卡片却长在长列表里 —— 所以这条策略留给宿主各自声明，共享资产不替宿主做决定。

**头部固定**：详情页的 `dhead` / `filters` / `sortrow` / 提示行，全部页的 `sortrow` / 提示行，
都写在 `<scroll-view class="scroller">` **之外**，是 `.screen`（纵向 flex）的固定子项。
只有事项列表参与滚动 —— 列表再长，返回键、「调整顺序」、手势说明都留在原位。
每个固定块都必须写 `flex: 0 0 auto`：光靠 `.screen` 的 `flex-direction: column` 不够，
不写就是默认的 `flex: 0 1 auto`，屏幕不够高时会被压扁（`.scroller` 有 `flex:1` + `min-height:0`，
会优先抢空间）。mp-check 的第 4 条检查专门盯这件事，防止头部被改回滚动区。

**提示行为什么钉在「调整顺序」下面**：它原来是列表最后一行，长列表里要滑到底才看得到，
等于没有。现在紧跟在操作入口下方，且是**固定头部**的一部分，任何滚动位置都可见。
高度用 `height: 46rpx` + `line-height: 46rpx` 撑出来 —— 原来用 `padding: 4rpx 0 12rpx`
（上 4 下 12）撑，文字在那一行里明显偏上。**要垂直居中就用等值 line-height，
别用上下不对称的 padding。**

**操作组为什么是条件渲染，而不是「常驻 + 被卡片盖住」**：早先 `.rowacts` 一直渲染在
`.row-in` 底下，靠卡片的不透明背景遮住。可拖动排序一改 `translateY`，卡片从原位挪开，
底下的按钮组就整块露出来了；已完成的行 `opacity:.5`，按钮更是直接透过来。
现在渲染条件是 `!sortMode && swipeKey===item._id`——**只有这一行正被滑开时才有这一层**。

代价是「收起」必须做成真正的收起：`onRowEnd` 里位移不到阈值就把 `swipeKey` 一并清空
（只把 `swipeX` 归零的话，按钮还挂在 DOM 里，只是被卡片盖住）；点已滑开的卡片同理。
另外 `onRowMove` 的节流基准要取「这一行自己的当前位移」，直接拿 `data.swipeX` 比，
在另一行正滑开着时基准是错的。

**排序模式为什么做成显式开关，而不是「长按直接拖」**：

1. 「整屏按下即拖」会让列表再也滚不动 —— 拖动与滚动抢的是同一串 `touchmove`；
2. 长按可以把手势分开，但没有视觉提示，新用户发现不了。

于是做成「显式开关 + 卡片右侧的拖动手柄」：模式解决「什么时候能拖」，
手柄解决「拖和滚怎么共存」。进入排序模式后：筛选胶囊、详情页 `⋮` 菜单被锁
（`.lock`：看得见点不动），**左滑操作组整个不渲染**（`wx:if` 里带上 `!sortMode`），
点卡片不编辑，底部换成固定的「完成」条（同时替掉「在此象限新建」和 Tab）。

切换视图（Tab / 返回 / 进象限）会自动退出排序模式；`render()` 里**故意不重置** `sortMode`，
否则每拖一次都会被落库后的重绘踢出排序模式。

**为什么「拖」和「滚」必须分到两个元素上**：两者都是纵向手势，落在同一个元素上就必然互斥 ——
要么拖不了，要么滚不了。手柄（`.dh`）用 `catchtouchstart` / `catchtouchmove` / `catchtouchend`
把事件从滚动区手里截走，卡片本体仍然是 `bind`，事件照常冒泡给 `scroll-view`。
一张卡片因此有了两块互不干扰的区域。**手柄上必须是 `catch`，卡片本体必须是 `bind`**
（手柄只用 `bind` 拦不住，会一边滚一边拖；卡片本体误用 `catch` 则整个列表再也滚不动），
仿真测试的第 15 组把这两条都钉住了。

**拖到边缘时列表自己滚**：手柄解决了共存，但手正按着手柄不放，腾不出第二根手指去滑列表。
所以手指贴到滚动区上下缘 96px 以内时，`runAutoScroll` 每 40ms 推一次 `scrollTop`。
两个细节不能省：

1. **行位置快照要跟着滚动平移**。`bindscroll` 报来真实滚动量，`_dg.rects` 整体减去它 ——
   手动滚、自动滚共用同一条回路，所以不会漂。
2. **卡片在屏幕上的位置 = 拿起时的位置 + 手指位移**，不是直接累加 `clientY`。
   写成 `dg.base0 + (clientY - _dgY0) - rects[from].top` 之后，列表滚多少，
   `rects[from].top` 就抵消多少 —— 列表没滚时它正好退化成原来的 `clientY - _dgY0`。
3. 滚到顶/底要能收手：`setData({scrollTop})` 后**不能立刻**判断有没有生效
   （`bindscroll` 是异步回来的，`_scrollTop` 还没更新），必须放到下一拍开头比。

**拖动的两条 setData 通道**（沿用左滑那套节流思路）：

1. `dragY` —— 被拖卡片跟手指走的位移，**每个 touchmove 都变**，但只推一个数字；
2. `shift` —— 其余卡片的让位量，**只在跨过某行中线时才变**，不需要每帧重算列表。

行位置在「拿起」时用 `boundingClientRect` 量一次就够，之后只按 `bindscroll` 报来的滚动量整体平移
（拖动期间布局没变，不必重新查询）。**但这个回调是异步的，必须设防**：回调回来时这一次拖动
可能早就结束了（手指点一下就抬走、中途切了视图、或者已经开始了新的一次拖动）。
所以 `startDrag` 每次自增一个 `_dragSeq` 代号，回调里三道闸一起关 ——
代号没变 + 仍在拖动中 + 拖的还是同一行，否则直接丢弃。

> 早先这里**无条件**写入 `_dg`，于是留下一个「僵尸拖动」：此后每一次 touchmove
> （包括正常滚动列表）都被 `applyDragMove` 接管，拿过期坐标算出错的让位位移，
> 把整个列表重排一遍 —— 用户看到的就是「列表一多，滑动时卡片乱跳、滑到的块都消失」。

**跟手通道必须量化 + 去重**（第 15 轮修的「拖动明显卡顿」）：

`dragY` 出现在**每一行**的 `style` 表达式里，所以每 `setData` 一次，整个列表的样式都要重算一遍。
而 `touchmove` 在真机上能到 60~120Hz —— 原来的写法是每个 touchmove 无条件推 `dragY`，
亚像素的位移屏幕上根本看不出来，却让每一帧都被判成「变了」而重复推送。
现在位移先 `Math.round` 成整数 px，再拿 `dg.pushedY` 去重：**同一像素格内的连续 touchmove 直接吃掉**。
落点判定也改用这个整数位移（屏幕上就是它，判定基准得跟渲染一致）。

配套的两条：

- `onRowStart` **不再**在 `touchstart` 就 `setData({dragging:true})`。`dragging` 只负责给这一行
  开「关掉过渡动画」的类，必须与第一帧位移同时到场；早推等于每次碰卡片（点一下、想滚列表、
  按手柄）都白触发一次全列表重渲染。现在由 `onRowMove` 在第一次真正产生位移时随位移一起推。
- `.row-in.lift` 加 `will-change: transform`。被拖动的那张卡片每帧都在挪位置，上面那圈 28px
  模糊的阴影若跟着重绘，单帧要重画十几万像素的高斯模糊。提升成独立图层后移动只是合成。
  这跟「静止的行一律不挂 transform」是同一条思路的两面：图层很贵，只给真正在动的那一个用。

**还有一道「量行位置在途」的闸**（第 15 轮修的「按住拖不动，要试好几次才成功」）：

`_dragSeq` 防的是「迟到的回调装上僵尸拖动」，但它防不住反面。`measureRows` 要过渲染层一个来回
（十几到几十毫秒），这期间 `_dg` 还是空的，于是 `onRowMove` 会在**每一个 touchmove** 上
再喊一次 `startDrag` —— `_dragSeq` 被反复自增，把在途的回调全部作废，`dragY` 被反复压回 0。
**手指一直在动、touchmove 不停，回调就永远等不到落地。**

修法是加 `_dgP`：量行位置在途期间只认第一次调用，后面的一律忽略；拿到 `_dg` 之后闸自动松开
（`onRowStart` / `endDrag` / 收尾分支也会清）。**这个坑的隐蔽之处是它只在真机出现**——
仿真测试的桩默认同步回调，永远复现不了；第 22 组专门把测量改成排队来复现它，
并带一条反向对照（手动拆掉闸，同样的手势立刻反复重来），确保断言真的抓得到它。

滚动开关（`scroll-y`）现在**常开**，任何模式的任何时刻都不去动它。
曾经的做法是进排序模式时一次性关掉（更早还试过绑 `dragOn`，手指一动就关）——
但滚动是**视图层**在 `touchmove` 那一刻就启动的，`setData` 关得晚半拍：
列表已经跟着手指滚了、卡片同时又在对列表重排，两边打架。
**靠改配置去抢手势是抢不赢的**，正解是把两种手势分给不同元素（见上面的手柄）。

**跨象限拖（仅「全部」页）**：目标行不在同一分段时不做让位动画——各行高度不一，
硬算必然错位——改为把目标分段整段高亮，并显示「松手移到这里」。松手后事项的 `quad`
跟着改，源/目标两个象限一起重排。

**已知限制**（都在可接受范围，需要时再补）：

- 拖动**必须从手柄开始**：手指落在卡片左侧正文上拖，那是在滚列表。这是刻意的取舍 ——
  手柄是唯一能把「拖」和「滚」干净分开的办法（见上）。换来的是排序模式终于能滚。
- 自动滚只在滚动区上下缘 96px 以内触发，速度固定（14px / 40ms ≈ 350px/s），
  不做「越靠边越快」。列表特别长、又要把卡片从最底拖到最顶时，会稍慢。
- 手柄的视觉提示只有那三道横线 + 顶部提示行文案，第一次用需要看一眼说明。

## 八、已确认的取舍

- **提醒推送只在「有提醒时间、且提前量不是『不提醒』」时才请求订阅授权**。用户明说不要通知
  还弹订阅框，既是骚扰，也不符合微信对「订阅要有真实触发场景」的要求。详见 §十二。
- **分页**：`fqTodo` 里 `PAGE_CAP = 500`。个人待办够用；超过需要加分页或游标。
  `fqRemind` 的拉取同样是 `CAP = 500` —— 这也是提前量**必须预计算成 `pushAt`** 的原因之一
  （放宽扫描窗口会把这个上限撞成「静默漏推」，见 §三）。
- **左滑手势**：走 JS `touchstart/move/end` + 单个数值 `setData` 节流。
  列表很长（>100 条）时可改 WXS 事件在视图层直接改样式，进一步省掉逻辑层通信。

## 十、几条不变量（改样式前先看）

都是「就差几像素」的坑，且全部用截图像素测量定位过，不是猜的。

| 坑 | 现象 | 原因与做法 |
|---|---|---|
| 在 `scroll-view` 上写 `display:flex` 让子项变 flex item | 胶囊标签顶部被削平、文字不居中 | 胶囊仍按行内盒排在文字基线上，被 scroll-view 的 `overflow:hidden` 裁掉约 13px。**flex 容器必须放进 scroll-view 内部**（`.cats-inner`） |
| 给纵向 flex 容器用 `max-height` 撑高度 | 抽屉底部按钮压在表单内容上 | 容器主轴尺寸不确定时 `flex-shrink` 不生效，主体连同内容溢出容器盒。**主体自己封顶**（`.sheet-body` 的 `max-height`），容器高度 = 三段之和 |
| 用 `grid: 1fr 1fr` 做两列等分 | 一列宽一列窄 | `1fr` = `minmax(auto,1fr)`，`auto` 下限取 min-content，长文本会把列顶宽。改用 `flex: 0 0 calc(50% - 7rpx)` + `min-width: 0` |
| 固定高度的容器上叠 `padding-bottom: env(safe-area-inset-bottom)` | 底部 Tab 被一条线拦腰穿过 | border-box 下安全区会从固定高度里被抠掉。**安全区加在固定高度之外**（高度写在 `.tb`，安全区留在 `.tabbar`） |
| 自绘图标改尺寸只改 `width/height` | 加号变成「†」 | 基类的 `flex: 0 0 28rpx` 没跟着改，盒子宽高不一致，伪元素按高度定位就跑偏。尺寸与 `flex-basis` 必须成对改 |
| `transform: scale()` 做点击反馈 | 象限看起来会缩水 | 在「尺寸必须恒定」的矩阵上改 `opacity` |
| 拖动卡片上的 `transform` 动画 | 卡片在动画期间被拽回原位 | 跟手位移由 `.row-in` 的内联 `transform` 承担，动画只能加在内层（`.row.pulse .row-in .tx`）。另外动画由 class 驱动、class 不变就不重放，所以「只抖一次」必须让那个 class 只短暂存在（`sortPulse` 380ms 后摘掉），不能挂在 `sortMode` 这种整段期间都为真的状态上 |
| 靠「上层的卡片盖住」来隐藏下层的按钮 | 已完成的行左滑后露出一个空面板；拖动时按钮整块露出来 | 遮挡只在布局静止时成立。操作组改成条件渲染（`!sortMode && swipeKey===item._id`），并保证「收起」时把 `swipeKey` 真正清空——只把 `swipeX` 归零的话按钮仍在 DOM 里 |
| **图标内部元素的 class 与页面级 class 重名** | 删除图标不居中：桶盖是正的，桶身整体右偏约 21rpx | 图标里那个 `<view class="body">` 同时命中了页面级的 `.body{padding:24rpx 32rpx 0}`（滚动内容的内边距容器）。绝对定位时左右 padding 相加 64rpx，远大于原定 22rpx 宽，桶身被撑到约 68rpx。**图标内部不要用会和页面 class 重名的名字**（`.lid` 没冲突就渲染正常，正好是一组对照）；定位一律「显式 width + `left:calc(50% - w/2)`」，不写 `left`/`right` 对 |
| 把该固定的头部写在滚动区里 | 列表一长，返回键、「调整顺序」、手势提示全被滚走，够不着 | `dhead` / `filters` / `sortrow` 必须是 `.screen` 的直接子项、且写 `flex: 0 0 auto`。有 mp-check 第 4 条守着 |
| 用上下不对称的 padding 撑一行文字的高度 | 提示文字在那一行里明显偏上 | `padding: 4rpx 0 12rpx` 上 4 下 12。**要垂直居中就用 `height` + 等值 `line-height`**（`.swipecue` 是 `46rpx` / `46rpx`） |
| 象限色底上的灰字（`--ink3`） | 详情页提示行几乎看不清 | 详情态整屏吃象限色，`.ink3` 的对比度不够。`.screen.detail-mode` 下把这类文字改成 `rgba(255,255,255,0.72)` |
| 总览页给矩阵写死高度 | 屏幕矮一点就多出一条可滚动的尾巴，高一点就是一片留白 | **总览页不套 `scroll-view`**：`.ovbody` 用 flex 分配剩余高度（矩阵容器 `flex:1`、饮水卡 `flex:0 0 auto`），矩阵内部按容器均分（`.grid.fill` → `height: calc(50% - 7rpx)`）。「一屏装满」是 flex 分配出来的**结果**，不是量出来的巧合 —— 所以别再给 `.q` 写死高度，更不要用 JS 去算屏幕高 |
| **绝对定位元素挂错了参照系** | 矮屏上悬浮「+」压住「今日饮水」的读数 | `.fab` 原本挂在 `.screen`（`position:fixed`）上，于是 `bottom` 的含义是「距屏幕底」，只能由 JS 按 `tab 高 + 安全区` 算成 px；可它要落的那一格高度是 flex 分配出来的 —— 屏幕一变矮就对不上。**把 `<fq-fab>` 挪进 `.ovgrid`、给 `.ovgrid` 加 `position:relative`**，坐标就成了「距矩阵右下角」的常数（`right:24rpx; bottom:22rpx`，与 `.q` 的 padding 26/24/22 对齐），矩阵变矮它跟着走。⚠️ 组件是 `virtualHost`、没有自己的节点，`.fab` 是 `.ovgrid` 的**直接子节点**，所以 `relative` 必须加在 `.ovgrid` 上 |
| **共享控件里替宿主做决定** | 把它上提到 `app.wxss` 后，长列表里每张卡片底部多出一条按着滑不动的死区；圆点「到头了」的悬空提示也看不见了 | 共享块只定**规格**（尺寸 / 圆角 / 过渡 / 抓取反馈），**策略留给宿主**。`touch-action: none` 只有总览页那张饮水卡禁得起（那屏本来就不滚），卡片长在长列表里则必须放过纵滑；`overflow: hidden` 一加，0% 与 100% 时半个悬在轨道外的圆点就被裁掉了 —— 而那个悬空正是「到头了」的提示 |
| **两条同款控件各写一份样式**（`fq-water.wxss` 里的进度条） | 平时看不出，改厚度时只改一处，于是「饮水的条比事项的粗一点」——**谁都不会报错，只会越走越歪** | 出现第二个用户时立刻**上提到 `app.wxss`**，用 `var(--wt)` 把颜色参数化（共享资产不认识任何具体颜色，所以在两个语境里都成立）。搬家后用「改名成 `.xbar` 让 `arch-check` 逐字比一遍声明体」的方式验过等价性 |

标签（`.tag`）要固定 `height` + 等值 `line-height`：只靠 padding 撑高时，含拉丁字母的
「P3」与纯中文的「工作」基线不同，视觉上一个偏头一个居中。

## 十一、共享家庭（一份清单两个人用）

### 模型

**一个家庭 = 一份共享的四象限清单。** 数据不挂在「人」上而挂在「家庭」上：
你加入对方的家庭，看到的就是对方的清单；退出，就回到自己那份。

首次进入时自动给你建一个「我的家庭」，你现有的全部待办就在里面。
想要家人共用同一份，一方点「生成邀请码」把 6 位码（或直接转发小程序卡片）给对方，
对方「加入家人的家庭」即可 —— **加入只是切换当前家庭，不搬运也不删除任何数据**，
自己那份一直原地留着，随时退出就能回。

一个人可以同时属于多个家庭（自己的一份 + 加入别人的），但同一时刻只有
`fq_members.active === true` 的那条是「当前家庭」。所以 `ensureFamily` 每次都会做
「查成员表 → 拿 fid → 读家庭」这两步，代价很小。

### ⚠️ 铁律：`fid` 只能由服务端推导

这是整个改动里**唯一会出安全事故的地方**，动它之前先读完这段。

云函数用的是**管理员权限，会绕过数据库安全规则**。所以「把集合权限设成仅创建者可读写」
这道防线对云函数形同虚设。真正拦住越权的是代码：

- 每个 action 的第一步都是 `ensureFamily(OPENID)`，`fid` 由 `fq_members` 查出来；
- **所有查询和写入都用 `ctx.fid`，没有一处从入参取 `fid`**；
- `where` 一律写成 `{ _id: id, fid: ctx.fid }` 双条件（改/删/拖排序都是）；
- 解析不出家庭时**直接拒绝**（fail closed），绝不回落到 `_openid`。

如果哪天为了「少查一次库」把 `fid` 改成客户端传参，就等于把全部家庭的数据敞开 ——
任何人构造一个请求就能读走别人的清单。`test-cloudfn` 的第 [12] 组就是专门钉这条的：
它会在请求里硬塞别人的 `fid`，断言改 / 删 / 建 / 批量删全部无效。

同理，**分权的地方也都在服务端**：`clearAll` / `genInvite` / `renameFamily` 校验
`fam.ownerOpenid === openid`。客户端把入口藏起来只是体验，不是防线。

### 邀请码

6 位，字符集是 `23456789ABCDEFGHJKMNPQRSTUVWXYZ` —— 剔掉了 `0/O/1/I/L` 这些抄下来会认错的。
24 小时有效，可以随时重新生成。生成与校验两端都做归一化（大写、去空格与连字符），
所以抄成小写、手滑带空格也能进。

**码只回给创建者**（`familyInfo` 里对非创建者返回空串）。成员看不到码，就没法随手转发
把无关的人拉进来。再加一道：家庭成员上限 20 人。

分享路径 `pages/index/index?code=XXXXXX` 会在 `onLoad` 里被接住，首屏加载完自动加入 ——
所以「把卡片转给家人」是最省事的邀请方式，不用手抄。

### 自动同步：为什么用轮询而不是 `watch()`

页面可见时每 8 秒带本地 `rev` 问一次云函数：rev 一致只回一个数字（几十字节），
不一致才把整份数据带回来。配合乐观更新，体感上就是「家人改了我这边自己就变了」。

**没有用云数据库的 `watch()` 做真·推送**，是因为它要求把集合读权限放开给客户端，
等于把「云函数是唯一数据出口」这条底线破掉 —— 为一个几秒的延迟改善，
换一个「任何人可遍历全库」的口子，不划算。真要上推送，正确顺序是**先给集合配
自定义安全规则**（注意 `get()` 只能按文档 ID 精确取，所以成员记录得用 openid 当文档 `_id`），
再改用 `watch`，不要跳步。

轮询有三个必须让路的时机，缺一个都会出「我点了一下，界面闪回去了」这类投诉：

| 时机 | 为什么必须让路 |
|---|---|
| 正在拖动排序（`sortMode`） | 整张列表会在手指底下被换掉 |
| 编辑抽屉开着（`sheetOpen`） | 列表在身后被换掉，保存会落到一条已经不在的行上 |
| 本地还有没落库的写操作（`pendingWrites > 0`） | 服务端快照会盖掉还没提交的乐观更新，用户看到自己刚点的那一下被弹回去 |

`pendingWrites` 在 `callCloud` 里按 action 名单自增自减（成功失败都减，否则一次
网络异常会让同步永远让路，静默停摆、极难查）。`test-reorder` 的第 [19] 组把一次写操作
挂起不 resolve，专门验这三条。

轮询随 `onShow` / `onHide` 起停 —— 后台不再请求，也就不烧额度。

### 老数据迁移（v3 之前的数据）

v2 及以前，事项和分类只有 `_openid`、没有 `fid`。升级后的第一次 `bootstrap` 会：

1. 建一个「我的家庭」+ 一条 `owner` 成员记录；
2. 把该 openid 名下**所有没有 `fid` 的分类与事项一次性认领**进这个家庭；
3. **不再播种** —— 否则老用户会看到自己的数据里混进 5 条示例。

这一步不能省，漏了老用户升级后会看到一个空列表，以为数据丢了。有 `test-cloudfn` 第 [11] 组守着。

### 分类的管理：长按删除 / 改名

分类原来只能新增，不能删也不能改名。现在入口在**我的页的「分类」卡片**上：**长按**任意一行
弹出操作面板（重命名分类 / 删除分类）。点整行仍然是「切到这个分类」——
那个是高频操作，不能被破坏性动作侵占；长按本身没有任何视觉提示，
所以卡片底部常驻一行「长按任意分类，可重命名或删除」补可发现性。

小程序有明确规定：**绑了 `longpress` 并触发之后 `tap` 不会再触发**，所以两种手势不打架。

删除的权限按**破坏力**分两层，不搞一刀切：

| 分类状态 | 谁能删 | 为什么 |
|---|---|---|
| 空分类 | 任何家庭成员 | 和「新增分类」全员可用对称，删错了再建一个就是 |
| 非空分类 | **只有家庭创建者** | 它底下可能躺着家人录的条目，破坏力和「清空全家数据」同级，用同一把尺子 |

非空分类的删除还要先决定**这 N 条事项去哪**，两个出口：

- **移到其他分类**（默认推荐）—— 列出现有分类，选完一次调用完成「搬事项 + 删分类」，数据不丢；
- **连同事项一起删除** —— 红色入口，**再确认一次**，文案里点明「家庭成员录入的也在其中」。

空分类没有这个分支，一次 `wx.showModal` 确认即可。

三条不能省的约束：

1. **「这个分类底下有没有事项」必须服务端重新数一遍**，绝不能采信客户端传来的判断。
   否则构造一个不带 `moveTo` 的请求，就能绕过界面上的确认直接抹掉整个分类 ——
   同 `fid` 铁律：云函数跑的是管理员权限，会绕过数据库安全规则，一切判定都要在服务端重来一遍。
2. **搬事项的顺序是「先搬、后删分类」**。反过来的话中途失败会把事项连同归属一起弄丢；
   现在最坏也只是「分类还在、事项已经搬走」，可恢复。
3. **家里至少要留一个分类**。全删光之后「新建事项」会因为无分类可选而卡死。
   客户端先拦一道（省一个来回），服务端同样拦。

删掉的刚好是**当前选中**的那个分类时，`state.catId` 会指向一个不存在的分类 ——
必须回落到第一个，否则整个页面是一片空白，看着像「数据全没了」。这一步复用已有的 `fixCatId()`。

### 已知取舍

- **数据不合并。** 你加入对方的家庭就是看对方的清单，两边原有的数据不会合到一起。
  这是刻意的：合并要处理「同一个分类名」「两端 order 撞值」等一堆规则，
  而实际想要的通常只是「一起用一份」。
- **删分类是即时生效、没有回收站。** 非空分类给了「先移到别处」这个出口，
  但一旦选了「连同事项一起删除」就不可恢复。真要做回收站，得给 `fq_items` 加软删除标记
  并让所有查询过滤它 —— 那是另一个量级的改动。
- **家庭成员之间没有细粒度权限**：加入即可读可写（符合需求原意）。想保留私人待办，
  目前只能放在自己那份清单里、不加入对方的家庭。
- **页面下拉刷新是失效的**（`index.json` 有 `disableScroll: true`，且没开 `enablePullDownRefresh`），
  所以 `onPullDownRefresh` 实际是死代码。日常靠 8 秒自动同步，问题不大；
  真想要手动刷新，从「我的」页加一个按钮比修下拉更省事。
- **提醒推送受一次性订阅的额度限制**。「设一次提醒然后长期每月收到」在个人主体下做不到：
  长期订阅只对政务民生 / 医疗 / 交通 / 金融 / 教育等特定类目开放，个人主体只能用一次性订阅 ——
  用户点一次「允许」= 一条发送权，用完即止。所以每次设提醒都顺手攒一条；额度不够时那条提醒
  就发不出去（但会如实显示成「未送达」，不静默吞掉）。详见 §十二。
- **额度扣了就不退还**。发送失败（用户拒收、模板字段超限）时微信那边其实已经把额度消耗掉了，
  退回去反而不准；网络抖动这种小概率事件，退与不退都说得过去，选了简单的那边。
- **`miniprogramState` 现在是写死的 `trial`**。它决定用户点通知后跳哪个版本，没发布正式版时
  必须是 `trial`，否则点了会跳「该小程序未发布」。**正式发布之后要改成 `formal`** ——
  位置在 `fqRemind/index.js` 的 `MINI_STATE`（`test-remind.js` 会断言它当前是 `trial`）。
- **一条提醒只发一次**。发出去之后，**改提醒时间或改提前量**任意一个都会把它重新排进队列
  （`updateItem` 按「真的变了」复位 `pushed` 并重算 `pushAt`；只改标题不会误触发）。
- **提前量的默认值对存量数据也生效**：v8 之前所有提醒都写死「提前 10 分钟」，升级后老数据
  没有 `leadMin`，一律按默认的 **30 分钟**补齐（回填逻辑在 `fqRemind`）。这是有意的 ——
  否则「默认 30 分钟」这条规则对老用户就不成立。想让某条回到 10 分钟，手动选一次即可。

## 十二、提醒推送（订阅消息）

### 能力与边界

| 项 | 现状 |
|---|---|
| 什么时候发 | **每条事项按它自己设的提前量**（v8 起）。到点的时刻是预计算好落库的 `pushAt = remindAt - leadMin`，触发器每分钟跑一次，实际落在「该发时刻 + 0~1 分钟」之间 |
| 提前多少 | 可选 10 档：不提醒 / 提前 5 分钟 / 10 分钟 / 30 分钟 / 1 小时 / 3 小时 / 1 天 / 3 天 / 7 天 / 30 天。**默认「提前 30 分钟」** |
| 发到哪 | 微信「服务通知」（订阅消息），点开落在小程序首页 |
| 谁收到 | 只发给**设置这条提醒的人**（条目的创建者），不做全家广播 |
| 额度 | 个人主体只有**一次性订阅**：用户点一次「允许」= 一条发送权 |

⚠️ **「设一次提醒、以后每个月都收到」在个人主体下做不到。** 长期订阅只对政务民生 / 医疗 /
交通 / 金融 / 教育等特定二级类目开放，后台「长期订阅」那一栏是空的属正常。想多囤额度，
就多保存几条带提醒的事项、每次点一下「允许」（勾过「总是保持以上选择」之后不再弹窗，
但授权次数照常 +1，所以体感就是「点保存完事」）。

### 提前提醒时长（v8）

**在哪设**：编辑事项抽屉里，「提醒时间」下面多一行「提前提醒」。它**只在设了提醒时间时出现**
（条件渲染，不是置灰）—— 没有提醒时间就谈不上「提前多久」，而一个永远点不动的选项比不出现
更让人困惑，用户会以为「这里本该能选」。

**可选值与默认值**：

| 显示 | 值（分钟） | | 显示 | 值（分钟） |
|---|---|---|---|---|
| 不提醒 | `-1` | | 提前 3 小时 | `180` |
| 提前 5 分钟 | `5` | | 提前 1 天 | `1440` |
| 提前 10 分钟 | `10` | | 提前 3 天 | `4320` |
| **提前 30 分钟（默认）** | `30` | | 提前 7 天 | `10080` |
| 提前 1 小时 | `60` | | 提前 30 天 | `43200` |

⚠️ **这份白名单有三处副本，必须完全一致**：`miniprogram/utils/const.js` 的 `LEAD_OPTIONS`、
`cloudfunctions/fqTodo/index.js` 与 `cloudfunctions/fqRemind/index.js` 各一份 `LEAD_ALLOWED`。
云函数不能 `require` 客户端代码、两个云函数之间也不共享，只能各留一份 —— 靠
`test-remind.js` 读三份源码逐字比对防漂移。

**存到哪**：`fq_items` 的两个字段（见 §三）——

- `leadMin`：提前量本身。**只在有 `remindAt` 时有值**，没有提醒时间就是 `null`；
- `pushAt`：预算好的推送时刻 = `remindAt - leadMin × 60000`。`leadMin === -1` 或没设提醒时间时落 `null`。

两个都落库而不是查询时现算，理由写在 §三（逐条提前量表达不成单一扫描窗口，放宽窗口又会撞
`CAP = 500` 的静默漏推）。

**默认值怎么兜**（三种情况都要照顾到）：

| 情况 | 结果 |
|---|---|
| 新建 / 编辑时选了某一档 | 就是那一档 |
| 前端传了白名单以外的值（`null` / 字符串 / 小数 / 越界数字） | 服务端 `toLead()` 一律**回落到 30 分钟**，绝不回落成「不提醒」 |
| 存量的老事项（没有 `leadMin`，也没有 `pushAt`） | 打开抽屉时显示默认档；`fqRemind` 每轮 tick 顺手把它们按默认档补上 `leadMin` + `pushAt`（详见下面「老数据」那段） |

**「不提醒」（`-1`）的语义**：**保留提醒时间，只是不发通知。** 提醒时间照常存着、界面上照常
显示，只是不再排进推送队列（`pushAt` 落 `null`）。所以它和「清除提醒时间」是两件事 ——
后者把 `remindAt` 一起清掉，是「这条事项不设提醒」。

**授权没通过时会怎样**（这部分是**故意做成可见的**）：

| 环节 | 行为 |
|---|---|
| 保存时机 | 只在「设了提醒时间**且**提前量不是『不提醒』」时请求订阅授权。选了「不提醒」**根本不弹订阅框** |
| 授权被拒（`reject` / `ban` / `filter`） | **当场**弹一次 toast：「未授权，这条提醒不会推送到微信」。**不改数据、不弹 modal、不拦流程** —— 用户可能只是手滑点了拒绝，拦一个弹窗逼他重选比不提醒本身还烦人。**提醒时间与提前量照常保存** |
| 后续 | 到点那一刻 `fqRemind` 发现额度为 0，把它记成 `pushErr: 'no-quota'` 并标记已处理（不会变成每分钟重试的漩涡），我的页聚合成「N 条提醒未送达」，点开有解释 |
| 环境不支持（老版本微信 / 调用被限） | 静默跳过，当没发生过 —— 提醒本身已经存下了，只是这次没攒到额度 |

> 早先这里是**纯静默**的，理由是「没额度」反正会在我的页聚出来。但那要等**提醒到点之后**
> 才看得见：中间这几天用户会一直以为提醒是好的，直到没收到才回头怀疑 —— 而那时已经错过一次了。
> 把反馈提前到「设的那一刻」，代价只是一次 toast。

### 它为什么是独立的一个云函数

`fqTodo` 的铁律是「每个 action 第一步 `ensureFamily(OPENID)`」，而**定时触发器里
`getWXContext()` 没有任何用户上下文** —— 混进去就是给那条铁律开一个例外。另外官方规定
**一个云函数下只支持一个定时触发器**，独立函数的部署边界也清楚得多。`fqRemind` 只读事项
和分类，只写事项的 `pushed` 系列、老数据的 `leadMin` / `pushAt`（回填）与 `fq_subs` 的额度，
不碰任何业务增删改。

### 四条照抄官方文档的硬约束

| 约束 | 依据 |
|---|---|
| 触发器时区固定 **UTC+8**，cron 直接按北京时间写 | 云开发定时触发器文档 |
| **会重复触发，必须去重** | 官方原文「网络环境不稳定，微信可能会多次推送同一条消息」。做法是抢锁：`where({_id, pushed: _.neq(true)}).update({pushed:true})`，只有 `stats.updated === 1` 的那一次才真发 |
| cron 是**七段式**（秒 分 时 日 月 星期 年） | `0 * * * * * *` = 每分钟第 0 秒；最小粒度就是分钟 |
| 云调用要**声明 `permissions.openapi`** | `config.json` 里少了 `subscribeMessage.send`，发送直接没权限，而且报错很难懂 |

### 额度是「扣到了才发」

```js
// 先扣，扣到才发。反过来「先发、被拒了再回滚」会让这条提醒变成
// 已经烧掉机会的哑弹，而且回滚本身也可能失败。
where({ _openid, quota: _.gt(0) }).update({ data: { quota: _.inc(-1) } })
```

扣不到就把它记成 `no-quota`（我的页显示成「N 条提醒未送达」，点了会解释为什么），
**不静默吞掉**。额度是按人攒的，所以「未送达」也只数自己创建的那些 —— 家人那条没发出去，
不该记在你头上。

### 消息内容的五个槽

模板「待办事项提醒」勾了 5 个字段，代码里就得赋 5 个非空值，**少一个整条消息 47003 发不出去**。

| 槽位 | key | 装什么 |
|---|---|---|
| 事项名称 | `thing26` | `item.title`（≤ 20 字，超了按字符截断） |
| 事项类型 | `thing15` | 所在象限名（重要且紧急 / 不重要但紧急 / …） |
| 备注消息 | `thing12` | `item.note`，空则填 `-` |
| 事项主题 | `thing1` | 分类名，查不到则填 `-` |
| 提醒时间 | `time23` | `YYYY-MM-DD HH:MM`，**北京时间**（写死 +8 偏移，不信任容器时区） |

> ⚠️ 「提醒时间」这个槽装的是 **`remindAt`（什么时候到期），不是 `pushAt`（什么时候发的）**。
> 「提前 7 天提醒我交房租」时两者相差整整一周 —— 通知里该告诉用户的是「哪天要交租」。

> 模板只是一组**带编号的空槽**，微信那边不知道你的数据模型长什么样，每个槽装什么完全由
> 代码决定 —— 不存在「模板绑定了某个表单字段」这回事。编号毫无规律（26 / 15 / 12 / 1 / 23），
> 必须逐字从后台「我的模板 → 详情」里抄。

### 老数据（v8 之前的事项）怎么办

v8 之前提前量是**全局常量 10 分钟**，所以那批文档既没有 `leadMin` 也没有 `pushAt` ——
`fqRemind` 改按 `pushAt` 扫之后，它们的提醒会**一条都挑不到**，而且一点报错都没有。

所以 `exports.main` 里第一步就是 `backfillPushAt()`：每轮 tick 顺手补一页（最多 5 页，
避免某次 tick 长时间占着），按**默认提前量**（30 分钟）算出 `pushAt` 落库。补过之后
就挑不到它们了，开销随老数据减少而趋近于零。

顺序不能反 —— **先回填、再扫描**。反过来的话，刚升级的那一轮会把存量提醒整批漏掉
（它们本来就不在扫描范围里）。

三个细节值得记住：

1. **判据用「`leadMin` 缺失」而不是「`pushAt` 缺失」**：选了「不提醒」的新数据 `pushAt` 落的是
   `null`（字段存在、值为空），拿它当判据会反复扫到同一条、无限回填。`leadMin` 和 `pushAt`
   是同一次改动引入的，两者必同生同灭，所以「`leadMin` 缺失 ⟺ 老数据」这个判据是干净的。
   （⚠️ 但**别声称测试守住了这个选择** —— 见 §五.5 末尾的说明。）
2. **条件里带 `pushed: _.neq(true)` 和 `done: _.neq(true)`**：已经推过的、已完成的不必回填。
   用 `neq(true)` 而不是等值 `false`，是因为老文档里根本没有这个字段，等值条件挑不到它们。
3. **副作用是有意的**：存量事项的提前量会从原来写死的 10 分钟变成 30 分钟。
   不这么做，「默认 30 分钟」这条规则对老用户就不成立。

## 十三、日程

「今天将要干什么、明天准备干什么」—— 点月历上的任意一天就能写。（配套设计稿里的进度条那一项**没做**。）

**入口**：底栏第 2 个 Tab（总览 / **日程** / 全部 / 我的）。它和「全部 / 我的」一样是内存里的视图状态，
不走路由 —— 整个小程序仍然只有 `pages/index/index` 一个页面。

**布局**：月历固定在顶部，日期头 + 两张计划卡 + 当天事项一起滚动。
点日期是这一页的核心动作，日历要是被列表滚走，想换一天就得先滚回去。

### 两条容易踩的口径

1. **「这天的事项」= 提醒时间落在那一天**。`fq_items` 里**没有**日期字段，只有 `remindAt`，
   所以这一段的语义照实写，不假装它是排期表。将来真给事项加上 `dueDate` 时，要改的是
   `buildSchedRows()` 这一个函数**加上**月历圆点的口径 —— 两者必须同时改。
2. **月历上的圆点与下面的事项列表必须是同一套判据**（都由 `remindAt` 归堆）。
   口径一旦分叉，就会出现「有圆点但点进去是空的」这种没人解释得通的状态。
   深点 = 有带提醒的事项，浅点 = 只写了计划；列表**不受分类筛选影响**（日程是跨分类的时间视图）。

### 为什么手写日历，而不是引一个组件

| 方案 | 结论 |
|---|---|
| 官方内置 `calendar` 组件 | **不存在**。网传「基础库 2.25.0 起支持」是错的，官方组件索引里没有它 |
| `picker mode="date"` | 可靠，但只是一个滚轮选择器、**没有圆点标记**，而圆点正是这一页的核心价值 |
| 第三方（Vant Weapp `calendar` / wx-calendar） | 要引入本项目**没有的** npm 构建链（`package.json` / `miniprogram_npm` / `node_modules` 全无），还要吞下一份包体积 |

自己写的是约 150 行**纯函数**日期运算（`utils/format.js`），可以脱离页面单测 —— `test-sched.js` 正是这么做的。

### 几个刻意的实现选择

- **固定 42 格（6 行 × 7 列）、周一起始**：高度稳定比省一行重要。
  表头用 `WEEK_MON`（`一…日`），**不要用 `WEEK`** —— 那个按 `getDay()` 的 `0=周日` 排，直接用会整体错开一列。
- **日期一律按本地时区算**：不用 `new Date('2026-10-09')`（iOS 按 UTC 解析，东八区会退一天），
  也不用 `toISOString()`（UTC，晚上 8 点后算到第二天 —— 于是「今晚的提醒」跑到明天的格子里）。
- **「今天 / 明天」标签由「选中日与今天差几天」推出来**，绝不写死。日历能选任意一天，
  写死的文案在选中 15 号时照样说「今天要做什么」—— 一个不报错、但会让人读错的谎。
- **顶部那行小标题固定显示「今天」，不跟选中日走**（`pageMeta = dateCN(todayStr())`）；下面 `.dayh`
  那行才是「我在看哪天」。两行都跟着点日历变的话，屏幕上就没有任何一处能告诉你
  日历上那个描边圈（今天）到底是几号了。⚠️ 验收这条**必须选一个非今天的日期** ——
  用今天验，「跟着选中日走」这个错误实现照样是绿的。
- **计划按人存**（`fq_plans`，见 §三），不按家庭；编辑复用已有的底部抽屉，不另开弹层。

## 十四、事项进度条

每个事项卡片底部一条进度条。**它和「完成」不是两个状态，是同一条状态线的两种读法**：
拖到 100% 就是完成，从 100% 拖回来就是自动撤销。数据落云的字段是 `progress`（0–100 整数），
与 `done` 的耦合钉在云函数里（见 §三、§四）。

### 为什么不新画一条，而是复用「今日饮水」

两条进度条本来就是同一个控件 —— 饮水卡那边的注释里甚至早就写着「圆点：白底 + 描边，
**与待办进度条同一规格**」。原先整套样式长在 `fq-water.wxss` 里，那时只有饮水一个用户；
事项进度条一来就有了第二个用户，于是按本项目的惯例**上提到 `app.wxss`**：

| 类 | 位置 | 说明 |
|---|---|---|
| `.wtrack` `.wbar` `.wfill` `.wknob` | **`app.wxss`**（共享块） | 触区 48rpx / 轨道 14rpx / 圆点 32rpx，两个语境读同一份 |
| `.wtrack.on` | **`app.wxss`** | 按住时的抓取反馈（轨道加深 + 圆点放大 1.24×） |
| `.water .wtrack` | `fq-water.wxss` | 只留宿主自己的两件事：它在卡片里的排版（`margin-top`）、`touch-action: none` |
| `.water.full .wfill` / `.wknob` | `fq-water.wxss` | 饮水达标后换成深一号的蓝（`--wt-d`） |
| `.prog` 系列 | `index.wxss` | 事项卡片自己的三件事：排版、读哪个颜色、右侧那个读数 |

三个细节值得单独记住：

- **颜色由宿主给，共享资产不认识任何具体颜色**：填充与圆点描边都读 `var(--wt)`。
  饮水卡定义 `--wt: #2e8fe0`，事项卡片定义成 `--wt: var(--qc, var(--ink3))` ——
  于是**进行中的进度条自然长成所属象限的颜色**，与左侧色条、详情页底色读的是同一个值。
  改颜色只需要动那一行。正因为它不认识颜色，两个语境才能共用同一份规格；
  否则迟早出现「饮水的条比事项的粗一点」这种谁都不会报错的漂移。
- **共享块里刻意没有 `overflow: hidden`**：圆点用 `left: <pct>%` + 负 margin 让百分比表示的是
  **圆心**，代价是 0% 与 100% 时圆点各有一半悬在轨道外 —— 那正是「到头了」的提示。
  加上裁剪就看不见了。
- **共享块里也刻意没有 `touch-action: none`**：理由见 §七（总览页不滚，长列表滚）。

### 颜色的唯一约束：绿只上图形，不上文字

| 状态 | 填充 / 描边 | 右侧读数 |
|---|---|---|
| 进行中 | 所属象限色（`--qc`） | 灰字 `NN%` |
| 已完成 | 完成绿 `--ok`（`#12a150`） | 灰字 `✓` |

⚠️ **读数区永远不放染绿的数字。** 完成绿对白的对比度是 **3.37:1**：够图形的门槛（3:1），
**跌破正文门槛（4.5:1）**。把「100%」这四个字符染绿，就是全页唯一一处不合规的文字 ——
所以 100% 时把数字换成对勾，而不是把它染绿。`index.wxss` 里这段注释和
`final-progress.html` 的自审计都各算了一遍这个数。

### 三处横向手势怎么分开

见 §七 的那张表：`touchstart` 用 `catch`（挡住左滑）、`tap` 用 `catch`（挡住进编辑）、
`touchmove` 用 `bind`（放过纵滑给列表）。

### 几个刻意的实现选择

- **读数区固定 68rpx 宽**（设计稿 34px）。这是「`9%` → `100%` 位数变化不会把轨道左右推挤」的
  唯一保证 —— WXSS 里 `font-variant-numeric` 不保证生效，靠固定宽度 + 右对齐顶上。
  换成对勾之后它仍占同样宽度，所以**完成那一刻轨道不会突然变长**。
- **拖动过程中只走单行路径 `setData`**（`rows[i].pct` / `sections[j].rows[i].pct`），
  不走 `render()`：列表不重排、统计条不重算、其它卡片一个字节都不动。
  两个视图共用同一个模板却落在**两棵不同的数据树**上，`progPath()` 只看当前视图那一棵 ——
  两棵都扫的话，切视图那一瞬可能同时命中同一个 id，改错一棵的表现是
  「数据对了、屏幕没动」，最难查。
- **松手才落库**。拖动期间每帧发一次云函数就是几十个并发请求，而且它们还可能乱序到达 ——
  最后到的那个不一定是你最后拖到的值。
- **百分比换算的 `rect` 由调用方传进去**，不让 `progPctAt` 自己读 `this._pg`：
  `onProgEnd` 在落库前会先把手势状态清掉，那时再读就什么都读不到，而这条路径恰好是
  「点一下圆点跳过去」—— 它会**整条静默失效**（不报错、不落库、进度不动，看着像没点到）。
  这个 bug 是写测试时抓到的，不是想出来的。
- **纵滑永久放弃本次手势**（判据与左滑一致：`|dx| <= |dy|` 就认输）。不永久放弃的话，
  用户「先往下滑、再往右滑」会把列表滚动硬生生掰成改进度。
- **排序模式下不响应进度条**，但手势**照旧被 `catch` 截住** —— 所以拖手柄时也不会
  误触发卡片左滑。分享的 CSS 类 `lock` 同时让它看起来是「锁住的」。
